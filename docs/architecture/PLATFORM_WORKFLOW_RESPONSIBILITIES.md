## 3. workflow 分工：已确认方向与其余候选

### 3.1. 术语与备选

业务 workflow 指完整业务动作，例如“完成练习并更新后续学习安排”；AI workflow 指其中需要模型／受控工具的执行过程，例如“改写查询 → 基于获准证据生成 → 检查输出格式”。后者可以包含多个节点，但节点完成不等于业务已成功提交。

当前情况：已有 Language 规划／评价同时涉及模型任务与业务结果，本地事务负责结果消费和业务状态一致性；PersonalNote 多数 AI 流程尚未实现。问题是直接把这些流程全搬进 AI 服务，可能把领域状态、权限和事务也一并迁走；只按现有模型 HTTP 调用拆分，又无法解释未来多节点流程。

| 候选 | 分工与收益 | 代价／影响 |
| --- | --- | --- |
| A：业务流程由领域服务组织，AI 服务执行受控 AI 子流程（L04 执行／消费方向已确认，其余逐项设计） | Language / PersonalNote 决定何时调用、提交什么输入、如何验收及落库；AI 可承载模型适配与有实际需要的 SAA Graph | 跨服务结果交付、业务 Run 与执行 Job 的关联需要新合同，不能直接沿用跨库事务 |
| B：AI 服务组织更长流程，通过受控业务 API／Tool 读取或请求动作 | 可以集中更复杂的 AI 编排与 checkpoint；领域服务仍执行权限与写入规则 | 回调、用户身份、工具授权、恢复和版本耦合增加；不因采用 SAA 就默认选择 |

两者均不得让模型／AI 服务任意写 Language 或 PersonalNote 数据库。统一 BYOK、语言隔离、只读 Vault 和用户确认写入均为既有约束。候选 A 不排除以后为明确流程选择 B，但不是提前构建通用 Agent 平台的授权。

### 3.2. 练习评价：执行与消费职责方向已确认，详细调用合同待设计

用户在比较“AI 保存结果”与“AI 仅执行、Language 保存全部结果”后，确认前者作为设计方向：

- AI 服务持有模型执行状态与可重新查询的执行结果；执行成功不等于业务消费成功，不要求 AI 数据库先记录业务消费成功。
- Language 持有评价任务、执行结果关联及业务消费结局；评价任务的唯一约束／状态条件更新与业务结果一起形成去重保证。
- Language 在同一个本地事务内保存评价结果并完成业务消费状态变更；重复处理已结束任务时读取已有结局，不再次产生业务影响。校验拒绝也形成明确失败结局，不无限重新消费同一无效结果。
- 区分业务任务 ID 与 AI 执行尝试 ID：同一次执行的网络重发复用执行 ID，明确的新模型调用才创建新的执行尝试并关联原业务任务。具体冲突、权限、版本及输入一致性校验待接口设计。
- 不预先要求跨事务持久化“消费中”；短暂校验与写入优先在本地事务内控制。如果后续确有长时间处理需求，再设计超时接管及旧执行者提交保护。

该确认仅确定职责和一致性方向，不批准表结构、结果回调／轮询方式、状态 enum、保留期限或恢复算法；其余流程的 Graph／Tool 分工仍待决定。目标调用链：

1. Language 校验用户和 `languageProfileId`，确认 Session 已完成，读取固定练习／rubric 输入并建立业务 Run。
2. 按待设计的接口，请求 AI 服务使用当前用户临时提供的 BYOK 执行语义评价；AI 不读取整份学习历史或直接修改领域表。
3. AI 返回可关联的执行结果／失败信息；Language 校验 Run、版本、归属、结果格式与 grounding，再保存本次结果。
4. 模型失败只影响语义分支，保留完成的练习与确定性评价；长期 Evidence 聚合仍属于后续 Language 业务能力。

关键未决：现有 Job 同时包含执行和消费信息，并与 EvaluationRun 在同一事务中消费；按新方向拆分职责时，需要设计结果交付、权限、保留及恢复协议，不能把现有整个 Job 原样搬进 AI 库后继续假设原事务仍成立。本例不是已经成立的 RPC 合同，不默认把两个数据库当成同一事务。模型返回已经发生后重新查询存储结果，不等于重新调用模型，不需要为了查询持久化 BYOK。

### 3.3. 示例二：笔记采集（目标链路，PROPOSED）

1. PersonalNote 校验本人权限，准备用户提交的文本或获准取得的来源内容，建立采集请求。
2. AI 服务使用本人 BYOK 生成 Markdown 草稿；是否需要多节点 Graph，按具体来源处理与验收需求决定。
3. PersonalNote 将可编辑草稿展示给用户；用户确认后，再由 PersonalNote 校验 Native 路径、版本与内容并写入。
4. 取消不保存；模型失败展示失败状态，不生成已确认笔记，不修改 Obsidian 来源。

这里“生成成功”“用户确认”“笔记已保存”是三个不同事件，不能以 AI Graph 成功状态代替后两者。

### 3.4. 共同失败与凭据边界

| 情况 | 已有约束／需要形成的合同 |
| --- | --- |
| 没有 BYOK、Key 失效或用户额度不足 | 不使用平台／其他用户 Key 兜底；已确认缺 Key 时提示并引导配置页，正常调用自动读取用户本地配置；Key 失效／额度不足的具体提示待设计。只读笔记、已有 Built-in 练习等非模型路径不应被设计成依赖模型 Key |
| 服务超时或连接断开 | C22 已确认：页面关闭／刷新后，已接收并启动的任务可在限定执行时间内继续；交互等待结束不等于执行结束。恢复先查已保存结果；未知执行先按供应商已验证的能力查询，无法确认则提示用户决定是否再次发起可能收费的调用，不把请求当作未发生并自动重试；新执行 ID 仍关联原业务任务 |
| 请求重复或结果迟到 | 业务请求、AI 执行、消费记录需要可核验关联；按各流程既有语义决定重放／冲突，不能把所有 POST 一概变成幂等 |
| 异步执行、进程重启或后台模型任务 | C22 已确认：已保存结果可经授权查询，无需模型 Key；明确未调用模型的任务，可等用户返回后由客户端自动提供可读取的本地 Key，经授权再继续。统一 BYOK 不允许为恢复把 Key 写入业务 Job、DB、Redis、Trace 或集群 Secret，不承诺设备离线且服务重启后的无人值守恢复；具体时限、状态、凭据生命周期和恢复接口待设计 |
| 模型输出／Tool 请求企图越权 | 结构格式校验不能代替业务语义、资源归属或工具授权；领域服务保留最终写入 authority |
